## Expected

- If a resident is labeled `STUCK` in `controller:status`, the live smoke window should corroborate that with no visible progress or an explicit stuck warning.

## Observed

- `npm run controller:status` at `2026-06-04T18:21:56.184Z` reported:
  - `res:agent` `STUCK`
  - `res:hans` `STUCK`
  - `res:qa-social` `STUCK`
- The same shared runtime then passed live smoke for two of those residents:
  - `res:hans`: `OK`, `actions=1`, `results=1`, `lastAction=move_to`, `lastResult=success`
  - `res:qa-social`: `OK`, `results=2`, `says=2`, `lastResult=success`, no smoke issues
  - `res:agent`: `WARN`, but not for stuckness; the issue was `observed_effect_timeouts:1` with recent actions, results, and speech still present
- Fresh disk artifacts also showed live activity:
  - `data/controller/logs/memory-usage.jsonl` contains `res:hans` writes/retrievals through `2026-06-04T18:22:19Z`
  - the same log contains `res:qa-social` speech/retrievals through `2026-06-04T18:23:00Z`
  - the same log contains `res:agent` arrivals/speech through `2026-06-04T18:22:51Z`
- `runtime-state.json` explains the mismatch:
  - `res:qa-social` has `stuckSince: 536`, `lastMeaningfulProgressAt: 367`, but live smoke still sees current speech and successful results
  - `res:agent` and `res:hans` have fresh `runtime-state.json` mtimes and recent activity, but `controller:status` marks any resident with `stuckSince` set as `STUCK`
- Source confirms the classification rule:
  - [`src/controller/observability/status-aggregator.ts`](/Users/james/Code/OnionDAO/rs6-nullcity-server/src/controller/observability/status-aggregator.ts:138) derives `STUCK` whenever `state?.stuckSince !== undefined && state?.stuckSince !== null`
  - [`src/controller/admin/status-cli.ts`](/Users/james/Code/OnionDAO/rs6-nullcity-server/src/controller/admin/status-cli.ts:11) reads only `runtime-state.json` plus recent trajectory, but the aggregator does not reconcile a stale `stuckSince` flag against current visible progress

## Assessment

- `controller:status` is currently too pessimistic for live operator truth.
- This is the same truth family as the earlier runtime-liveness concern, but the current cycle broadens it: the false-`STUCK` state is not isolated to `res:hans`.
- The narrow claim supported by this packet is:
  - `controller:status` over-reports `STUCK` when `stuckSince` remains set even though live smoke and fresh trajectory/log evidence show current resident activity.
